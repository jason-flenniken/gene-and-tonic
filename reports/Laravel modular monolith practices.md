# Build Laravel modules with enforced boundaries

For a Laravel 13.38 / Livewire 4.4 / Pest 5.3 demo that should model good modular-monolith structure, use **internachi/modular 3.0.2 with modules as Composer path packages in `app-modules/`**. Give each module a small public surface (contracts, DTOs, events, enums, exceptions) and keep everything else private. Enforce the split with Pest architecture tests, backed by Deptrac for the dependency graph and cycles. Laravel has no first-party module feature: the 13.x release notes and the Laracon US 2026 announcement roundup contain nothing on modules, and the roundup's "package skeleton" targets reusable packages, not app modules ([Laravel 13.x release notes](https://laravel.com/docs/13.x/releases), [Laracon US 2026 roundup](https://laravel.com/blog/everything-we-announced-at-laracon-us-2026)). The package choice matters less than the enforcement. Neither internachi/modular nor nwidart/laravel-modules documents any boundary enforcement ([InterNACHI README](https://github.com/InterNACHI/modular)), so a module is a folder until a test makes it a boundary. The weakest evidence is on the Livewire 4 side. The module-aware registration pattern below comes from reading Livewire and package source, not from running it, and the one integration package (`internachi/modular-livewire`) probably skips modules that contain only single-file components. Plan to register Livewire namespaces from each module's own provider, and spike that first. Evidence on Laravel-specific module practice is thin and mostly opinion (blogs, a Laracasts course, READMEs). I could not retrieve Laravel Beyond CRUD, Spatie material, or any Laravel post-mortem. Treat the architecture advice as reasoned convention, not settled consensus.

## How to read the evidence labels

Statements with a link are findings the researchers fetched. Text tagged **[Inference]** is reasoning built on those findings and has no source behind it. Text tagged **[Constructed, untested]** is code or config the researchers assembled from documented APIs; none of it was run. Text tagged **[Unverified]** marks a claim the researchers could not confirm, or sources that conflict. Everything in the recommended setup that is not cited is an inference. All version and date facts are as of 2026-10-24.

## internachi/modular wins on fit, but nothing wins on maturity

Three options are realistic, and the two packages are roughly equal in maintenance health. internachi/modular **3.0.2 (2026-03-23)** added Laravel 13 support, needs PHP >=8.3, has about 1.26M total downloads and 1,211 stars, and last had a main-branch push on 2026-05-21 ([releases](https://github.com/InterNACHI/modular/releases), [Packagist](https://packagist.org/packages/internachi/modular)). nwidart/laravel-modules **v13.0.0 (2026-03-19)** requires PHP ^8.3, has about 19.0M downloads and 6,217 stars, and last had a master commit on 2026-04-13 ([releases](https://github.com/nWidart/laravel-modules/releases), [Packagist](https://packagist.org/packages/nwidart/laravel-modules)). Neither has tagged a release since March 2026, which reads as stable and low-churn rather than abandoned **[Inference]**. Newer entrants (saeedvir, alizharb, studeo) have under 3,000 downloads each, and `studeo/modular` is days old ([Packagist](https://packagist.org/packages/studeo/modular)). Skip them.

The philosophies differ in ways that matter here. InterNACHI describes itself as "as much a set of conventions as it is a package": modules are Composer path packages that use Laravel's own package discovery, and its plugins auto-register routes, views, Blade components, translations, listeners, migrations, policies, and commands, with `--module=` on the `make:*` generators ([README](https://github.com/InterNACHI/modular), [3.0.0 notes](https://github.com/InterNACHI/modular/releases/tag/3.0.0)). nwidart uses its own `Modules/` layout, a `module.json` per module, generators configured in `config/modules.php`, and **runtime enable/disable**. InterNACHI's README itself recommends nwidart only for CMS-style apps with dynamically toggled third-party modules ([README](https://github.com/InterNACHI/modular)). This demo does not need toggling. nwidart's open issues also show some friction: inconsistent `module:migrate*` code paths (#2159), no cross-module listener auto-discovery (#2128), and no Vite hot refresh for module Blade files under a root config (#2120) ([issues](https://github.com/nWidart/laravel-modules/issues)). InterNACHI's own risks are a narrow maintainer base and, per its issue list, no nested modules (#141) ([issues](https://github.com/InterNACHI/modular/issues)).

The no-package route is credible and cheaper than it used to be. Laravel 13 discovers event listeners from multiple directories with wildcards (`->withEvents(discover: [__DIR__.'/../app/Domain/*/Listeners'])`) ([Events docs](https://laravel.com/docs/13.x/events)), and Livewire 4 has a native namespace API ([Livewire components docs](https://livewire.laravel.com/docs/4.x/components)). One 2026 post recommends plain folders under `app/Modules/`, one provider per module in `bootstrap/providers.php`, and Pest arch tests ([Wendell Adriel](https://wendelladriel.com/blog/modular-monoliths-creating-real-boundaries-before-reaching-for-microservices)). What you give up is auto-wiring of migrations, routes, views, translations, and policies, each of which a hand-written provider must replicate **[Inference]**. A claim that Composer path repos plus a per-module provider match what a package offers came from a search summary the researchers never opened **[Unverified]**.

My pick is InterNACHI **[Inference]**. The module-as-Composer-package model gives the demo a visible `composer.json` dependency declaration per module, which doubles as documentation of the module graph and a ready extraction path. The cost of leaving the package is low because modules are plain Composer packages, which offsets the bus-factor risk. Neither package has documented testing against Laravel 13.38 specifically, only the `13.x` constraint, and neither states PHP 8.4 support beyond ">=8.3" **[Inference: should work]**.

## A small public surface, events for writes, and data that stays home

The sources converge on one shape. Each module publishes interfaces bound in its own service provider, plus events and DTOs, and treats models, actions, and infrastructure as private. The advice is explicit: "Resist the temptation to access another module's models directly" ([Steve McDougall](https://www.juststeveking.com/articles/building-modular-systems-in-laravel-a-practical-guide)). A second write-up keeps `Domain` and `Infrastructure` private and routes cross-module reads through an interface the owner publishes ([Cenedy](https://cenedy.is-a.dev/blog/laravel-modular-monolith)). A strict hexagonal example goes further with ports and adapters ([oohegor](https://github.com/oohegor/laravel-modular-monolith)). That is the heavy end, and the same example is the only source that uses repositories. The pragmatic end uses thin controllers and one-use-case action classes ([Cenedy](https://cenedy.is-a.dev/blog/laravel-modular-monolith)). The Laracasts "Modular Laravel" series (25 episodes, last updated 2024-01-04) covers the same ground, but only episode blurbs were read ([Laracasts](https://laracasts.com/series/modular-laravel)). Shopify's Packwerk retrospective, from Ruby but about the same problem, adds the most useful warning: privacy enforcement pulled attention to API design and was dropped in Packwerk 3.0, and public APIs "need deliberate documentation and design, separate from dependency enforcement" ([Shopify Engineering](https://shopify.engineering/a-packwerk-retrospective)). I would not fight Laravel conventions to make classes private. Make the public/private split a **namespace convention** that tests can check **[Inference]**: `Contracts`, `Data`, `Events`, `Enums`, `Exceptions` are public. That list is also Cordon Modulith's default public set ([Packagist](https://packagist.org/packages/chrisabner/cordon-modulith)). I add `Testing` for owner-shipped fakes **[Inference]**. Everything else (`Models`, `Actions`, `Livewire`, `Http`, `Listeners`, `Policies`, `Providers`, `Services`) is private. I found no source evaluating facades as a module API, so keep them out of the cross-module surface.

Communication splits cleanly by whether the caller needs an answer. Reads that need an immediate result go through a published contract. Orders can ask Catalog for a price through `PriceLookup`. Side effects in other modules go through events: Orders saves inside `DB::transaction`, dispatches `OrderPlaced`, and Billing's queued listener creates the invoice, so a Billing outage delays invoices instead of rejecting orders ([Cenedy](https://cenedy.is-a.dev/blog/laravel-modular-monolith), [McDougall](https://www.juststeveking.com/articles/building-modular-systems-in-laravel-a-practical-guide)). Laravel's `ShouldDispatchAfterCommit` (added in 10.30) holds an event until the surrounding transaction commits and discards it on rollback; nested-transaction and observer edge cases are unverified ([Laravel News](https://laravel-news.com/index.php/laravel-10-30-0)). Sources disagree on payloads: one says pass IDs because serialized models go stale, another serializes the model ([Cenedy](https://cenedy.is-a.dev/blog/laravel-modular-monolith) vs [McDougall](https://www.juststeveking.com/articles/building-modular-systems-in-laravel-a-practical-guide)). I side with IDs and DTOs because a model in an event payload is an import of the owner's private class **[Inference]**. Several 2026 outbox packages exist (gpalyan/laravel-outbox 2.0.0 is the most complete), but none leads ([Packagist](https://root.packagist.org/packages/gpalyan/laravel-outbox)). In one process and one database, after-commit queued listeners give most of the benefit, so skip an outbox for the demo and make listeners idempotent **[Inference]**.

On data crossing the boundary, the evidence favors DTOs over Eloquent models but offers no hard consensus. The Laracasts course has dedicated DTO episodes, and the hexagonal example converts requests to DTOs at the controller ([Laracasts](https://laracasts.com/series/modular-laravel), [oohegor](https://github.com/oohegor/laravel-modular-monolith)). A forum thread names the real tradeoff: returned models leak relationships, while one big DTO tempts you to load unneeded relations ([Laracasts discussion](https://laracasts.com/discuss/replies/929803)). **[Inference]** Put each DTO in the providing module's `Data` namespace so consumers depend on the provider and never the reverse. Use `final readonly` classes on PHP 8.4. Add spatie/laravel-data only if you want edge validation and casting, and no source tested it here.

Data ownership is the thinnest area. The sources agree on per-module migrations and models and on not creating a module per Eloquent model ([McDougall](https://www.juststeveking.com/articles/building-modular-systems-in-laravel-a-practical-guide)). Cross-module foreign keys are treated as a conscious tradeoff: the Moduark analyzer warns by default, since a relational monolith may accept migration coupling for integrity ([Moduark](https://root.packagist.org/packages/cluion/moduark)). InterNACHI's migration docs say the referenced table's migration must sort first ([docs](https://www.mintlify.com/internachi/modular/guides/module-migrations)). I found nothing on table prefixes, cross-module Eloquent relations, or cross-module reporting. **[Inference]** Rules I would adopt: a module writes only its own tables; no cross-module Eloquent relations; foreign keys only to a stable upstream module (users, say), never between peers; cross-module reporting through a published query contract returning DTOs. Raw SQL joins and cross-module writes in transactions are invisible to static checks, a limit the Pest-based advice also notes ([Wendell Adriel](https://wendelladriel.com/blog/modular-monoliths-creating-real-boundaries-before-reaching-for-microservices)).

The shared kernel should be tiny and depend on nothing. The transferable (.NET) guidance: include only types that several modules genuinely need, such as base types, event contracts, and typed IDs; exclude DTOs and single-module utilities; and apply the test "if removing a type would break only one module, it doesn't belong" ([Milan Jovanovic](https://milanjovanovic.tech/blog/shared-kernel-pattern-modular-monolith)). Shopify kept a zero-dependency base package with CI to hold it that way ([Shopify](https://shopify.engineering/a-packwerk-retrospective)). The rule is that `Shared` depends on nothing and feature modules may depend on `Shared` **[Inference]**.

## Pest arch tests catch the common leaks; they are static and blind to strings

Pest's `arch()` API has the vocabulary needed: `not->toUse`, `toOnlyUse`, `toBeUsedIn`, `toOnlyBeUsedIn`, `ignoring()`, and wildcard namespaces (since Pest 3.8). It has custom presets that receive the app's PSR-4 namespaces, a natural hook for generating per-module rules ([Pest arch docs](https://pestphp.com/docs/arch-testing)). Pest 5.0.0 (released 2026-07-28; requires PHP 8.4 and PHPUnit 13) lists no architecture-testing changes in its announcement, which centers on the Tia engine, sharding, PHPStan and Rector plugins, and new expectations. The docs say no more than that, so the absence is not proof ([Pest 5 announcement](https://pestphp.com/docs/pest5-now-available), [releases](https://api.github.com/repos/pestphp/pest/releases?per_page=30)). The latest release seen was 5.3.3 (2026-10-18), so 5.3 is current.

The limits are structural **[Inference]**. Pest arch is static analysis of `use` and references. Container-resolved strings, config class names, morph maps, event names as strings, Eloquent relation strings, and raw SQL across module tables are invisible to it, and facades and helpers can hide a call. It also has no dependency graph, so it cannot see cycles or enforce a declared `depends_on`. Two documentation points need a scratch-repo check. A search snippet claims `not->toOnlyUse()` and `not->toOnlyBeUsedIn()` are unsupported, but the fetched docs say nothing of the kind **[Unverified: sources conflict]**. And the exact semantics of `toOnlyBeUsedIn` (sibling or subtree namespaces) are not documented beyond one example.

**[Constructed, untested]** A per-module deny-list is the low-noise starting point:

```php
// tests/Arch/ModuleBoundariesTest.php
$modules = ['Catalog', 'Orders', 'Billing'];
$private = ['Models', 'Actions', 'Livewire', 'Http', 'Listeners', 'Policies', 'Providers', 'Services'];

foreach ($modules as $m) {
    $forbidden = collect($modules)->reject(fn ($o) => $o === $m)
        ->flatMap(fn ($o) => array_map(fn ($p) => "Modules\\$o\\$p", $private))->all();

    arch("$m uses no other module's internals")
        ->expect("Modules\\$m")->not->toUse($forbidden);
}

arch('shared kernel depends on no feature module')
    ->expect('Modules\Shared')->not->toUse(['Modules\Catalog', 'Modules\Orders', 'Modules\Billing']);
```

Deptrac is the mature second gate. It lives at `deptrac/deptrac` (default branch `4.x`, PHP 8.2+) and shipped 4.7.2 on 2026-09-15. Its collectors can set `private: true` so a token is referenceable only from its own layer, and it supports baselines for legacy violations and graphviz output ([GitHub](https://github.com/deptrac/deptrac), [releases](https://api.github.com/repos/deptrac/deptrac/releases?per_page=5), [collectors docs](https://raw.githubusercontent.com/deptrac/deptrac/4.x/docs/collectors.md)). The PHP config format makes per-module layer generation by loop easier than YAML. I found no 2026 evidence of how many Laravel teams use it, so do not assume popularity. **[Inference]** Pest arch covers "who may use whom" inside the test suite, and Deptrac adds cycles, a graph, and baselines. Together they overlap, so keep Deptrac's ruleset coarse (module-to-module edges only) and leave the namespace-level private/public rules to Pest. The `private: true` behavior was not verified end to end.

The young Laravel-specific tools are tempting but risky. Cordon Modulith v0.1.1 (2026-09-29, alpha) offers `internal_access`, `undeclared_dependency`, and `cycles` rules, `#[PublicApi]` attributes, per-module `depends_on`, and a Pest `toRespectBoundaries()` expectation. It does not analyze code outside modules (such as `app/Http`) and misses string class names and docblock-only types ([Packagist](https://packagist.org/packages/chrisabner/cordon-modulith)). `happenv-com/laravel-true-modular-phpstan` v1.1.0 (2026-09-17) enforces the boundary through a PHPStan extension, but it is tied to a different module package ([Packagist](https://packagist.org/packages/happenv-com/laravel-true-modular-phpstan)). Both are weeks to months old and run on package READMEs alone, with no verification in a real project; adoption risk is real. PHPArkitect is a mature generic alternative to Deptrac with PHP-code rules and baselines ([GitHub](https://github.com/phparkitect/arkitect)). A homegrown PHPStan rule is feasible for per-file checks ([PHPStan docs](https://phpstan.org/developing-extensions/rules)), but it is more work than the demo needs.

Shopify's experience is the reason to adopt a baseline-and-ratchet habit even in a fresh app: "todo files" for existing violations blocked new ones, and their tools had blind spots (dynamic constants, routes) that let packages pass checks yet fail at runtime ([Shopify](https://shopify.engineering/a-packwerk-retrospective)). Deptrac baselines map to that habit **[Inference]**.

## Module-local tests, a central arch suite, and fakes owned by the provider

InterNACHI keeps `tests/` in each module and `php artisan modules:sync` adds a `Modules` testsuite to `phpunit.xml` (directory `./app-modules/*/tests`), skipping if one exists; 3.0.2 added `--no-phpunit` to skip that update ([ModulesSync.php](https://github.com/InterNACHI/modular/blob/main/src/Console/Commands/ModulesSync.php), [3.0.2](https://github.com/InterNACHI/modular/releases/tag/3.0.2)). Pest binds a base class by directory, and wildcard directories work, e.g. `->in('../Modules/*/Tests/Browser')` ([Pest configuring tests](https://pestphp.com/docs/configuring-tests)). Laravel's parallel runner creates one database per process (`name_test_1` and so on), so the MySQL user needs CREATE privilege ([Laravel 13 testing docs](https://laravel.com/docs/13.x/testing)). No source compares central versus in-module tests with data; the layout below follows conventions and reasoning **[Inference]**: unit and feature tests move with the module, while the cross-cutting arch tests and cross-module flows, which belong to no module, stay central.

**[Constructed, untested]** `tests/Pest.php` binding:

```php
pest()->extend(Tests\TestCase::class)
    ->use(Illuminate\Foundation\Testing\LazilyRefreshDatabase::class)
    ->in('Feature', 'Integration', '../app-modules/*/tests');
```

The isolation seam for cross-module dependencies is the published contract. Laravel's docs confirm the mechanics: bind a collaborator with `$this->instance(...)`, and mock listeners when testing code that dispatches events ([Laravel 13 mocking docs](https://laravel.com/docs/13.x/mocking)). **[Inference]** I prefer hand-written in-memory fakes shipped by the owning module (`Modules\Catalog\Testing\InMemoryPriceLookup`) over Mockery, plus an abstract contract test in the owner that runs against both the real implementation and the fake, so the fake cannot drift. For events, assert dispatch in the producer, test the listener directly in the consumer, and use `Event::assertListening` to prove wiring. The `Event::fake`, `fakeExcept`, and `assertListening` names come from prior knowledge, not from fetched Laravel 13 docs. A bare `Event::fake()` also fakes Eloquent model events, which can break factories and observers, so pass an event list.

CI should run the cheap static checks first with no database (Pint, PHPStan, the Pest `Arch` suite, Deptrac), then per-module test jobs, then an integration suite. Pest's Tia is for local dev: its docs say not to add `--tia` to the main CI pipeline ([Tia docs](https://pestphp.com/docs/tia)). Time-balanced sharding (`--shard=1/4`, `--update-shards`) is the supported way to speed up CI ([Pest 5 announcement](https://pestphp.com/docs/pest5-now-available)). Affected-module selection (changed directories expanded by reverse dependencies) is my design and has no published Laravel reference **[Inference]**. For a demo it is overkill.

## Livewire 4 gets a namespace per module, and Flux stays global

Livewire 4 has a resolver-based registry with three layers: `component_locations` (unnamespaced), `component_namespaces` (`ns::name`), and a programmatic `Livewire::addLocation()`, `addNamespace()`, and `addComponent()` API ([components docs](https://livewire.laravel.com/docs/4.x/components), [upgrade guide](https://livewire.laravel.com/docs/4.x/upgrading)). The researchers read Livewire's source for the following, which the docs do not state. The config keys cover only view-based (SFC/MFC) components, so class components in a module need the programmatic API. `Livewire::addNamespace()` registers only in Livewire's own finder and does **not** register a Blade view namespace, which only the config loop does. Namespaced lookups never fall through to other namespaces. And `make:livewire billing::invoice-table --class` needs `classPath` and `classViewPath` passed to `addNamespace` or the computed paths degenerate to the filesystem root, which is the researchers' reading of the code and was never reproduced ([Finder.php](https://github.com/livewire/livewire/blob/main/src/Finder/Finder.php), [LivewireServiceProvider.php](https://github.com/livewire/livewire/blob/main/src/LivewireServiceProvider.php), [MakeCommand.php](https://github.com/livewire/livewire/blob/main/src/Features/SupportConsoleCommands/Commands/MakeCommand.php)). Single-file components, the Livewire 4 default, resolve as `⚡name.blade.php` inside a namespace directory, and `make:livewire billing::invoice-table` writes `⚡invoice-table.blade.php` into the namespace's view path (same sources). The latest release at the time of research was v4.4.8 (2026-10-21) ([releases](https://github.com/livewire/livewire/releases)).

Neither module package registers Livewire components in core. `internachi/modular-livewire` 2.0.1 (2026-09-07) calls `Livewire::addNamespace` on Livewire 4, but the source scans only `*.php` files in `src/Livewire` and registers a namespace only for modules that have at least one class there. A module containing only SFCs may therefore never get its namespace registered. It also does not pass `classPath` or `classViewPath`, and its README still says Livewire ^3 ([source](https://github.com/InterNACHI/modular-livewire/blob/main/src/ModularLivewirePlugin.php), [Packagist](https://packagist.org/packages/internachi/modular-livewire)). Both gaps are code readings, not runtime findings. The nwidart counterpart (`mhmiton/laravel-modules-livewire` v7.0.0) passes all class arguments but also registers global unnamespaced locations, creating a name-collision risk ([source](https://github.com/mhmiton/laravel-modules-livewire/blob/master/src/Providers/LivewireComponentServiceProvider.php)). **[Inference]** The package-agnostic answer is a six-line registration in each module's own provider. That drops the dependency on `modular-livewire` and sidesteps the SFC-only gap:

```php
// Modules/Billing/src/Providers/BillingServiceProvider.php, boot()   [Constructed, untested]
$base = dirname(__DIR__, 2);
Livewire::addNamespace(
    namespace: 'billing',
    viewPath: $base.'/resources/views/livewire',
    classNamespace: 'Modules\\Billing\\Livewire',
    classPath: $base.'/src/Livewire',
    classViewPath: $base.'/resources/views/livewire',
);
Blade::anonymousComponentPath($base.'/resources/views/components', 'billing');
```

Pages use `Route::livewire('/billing/invoices', 'billing::invoices.index')`, which Livewire 4 requires for SFC/MFC full-page components; it returns a normal route, so groups, middleware, naming, and route caching work ([upgrade guide](https://livewire.laravel.com/docs/4.x/upgrading), [HandleRouting.php](https://github.com/livewire/livewire/blob/main/src/Mechanisms/HandleRouting/HandleRouting.php)). Layouts resolve per component through `#[Layout]`, `->layout()`, or the global `component_layout` (default `layouts::app`, i.e. `resources/views/layouts/app.blade.php`) ([pages docs](https://livewire.laravel.com/docs/4.x/pages)). That is exactly where the demo's existing base layout lives, so it can stay as the single app shell. The source shows no per-route-group default layout **[Inference from source]**, which argues for one shared shell and per-module layouts only where chrome truly differs.

Blade primitives come from Laravel. Both packages register `module::` view namespaces and class-component namespaces, and neither registers anonymous component paths ([ModuleServiceProvider.php](https://github.com/nWidart/laravel-modules/blob/master/src/Support/ModuleServiceProvider.php), [BladePlugin.php](https://github.com/InterNACHI/modular/blob/main/src/Plugins/BladePlugin.php), [README](https://github.com/InterNACHI/modular)). That is why the snippet above adds `Blade::anonymousComponentPath` explicitly. Flux is global: its install is app-level (`@import '../../vendor/livewire/flux/dist/flux.css'` on Tailwind >= 4.2, plus `@fluxAppearance` and `@fluxScripts` in the layout), `flux.css` carries its own `@source` lines, and the docs say nothing about modules ([Flux installation](https://fluxui.dev/docs/installation), [flux.css](https://github.com/livewire/flux/blob/main/dist/flux.css)). **[Inference]** So `<flux:*>` works in any module view with no wiring, and no module should `flux:publish` into its own directory, since published files land in app-global `resources/views/flux`. Put domain-agnostic composites in a `ui` module as anonymous components (`<x-ui::page-header>`), and prefix everything module-owned (`<x-billing::...>`, `billing::`) so anonymous names cannot collide. Record the dependency of modules on Flux and `ui` in the boundary rules.

For Tailwind 4 and Vite, auto-detection scans everything under the working directory except git-ignored files, `node_modules`, binaries, CSS, and lockfiles, and `@source` adds paths ([Tailwind docs](https://tailwindcss.com/docs/detecting-classes-in-source-files)). **[Inference]** `app-modules/` is a real, non-ignored directory, so module views should be scanned with no config. This is untested, and the `@source` glob syntax is not documented on the page the researchers read **[Unverified]**. Laravel's Vite plugin default `refresh: true` watches only `app/Livewire/**`, `resources/views/**`, `routes/**`, and a few others ([Vite docs](https://laravel.com/docs/13.x/vite)), so add module paths explicitly for hot reload. nwidart's open issue #2120 reports the same gap ([issues](https://github.com/nWidart/laravel-modules/issues)). Keep one CSS and one JS entry. Livewire 4 component `<style>` is scoped with CSS nesting and `<script>` is served as a raw file by a Livewire route, not through Vite ([styles](https://livewire.laravel.com/docs/4.x/styles), [SupportJsModules.php](https://github.com/livewire/livewire/blob/main/src/Features/SupportJsModules/SupportJsModules.php)). **[Inference]** That means no `@apply` or npm imports in component blocks, so use utilities in markup and keep component CSS tiny.

Cross-module UI composition has no documented Livewire feature. Livewire's primitives are `<livewire:is :component="$name" />`, `Livewire::exists()`, and browser events through `dispatch()` and `#[On]` ([events docs](https://livewire.laravel.com/docs/4.x/events), [LivewireTagPrecompiler.php](https://github.com/livewire/livewire/blob/main/src/Mechanisms/CompileLivewireTags/LivewireTagPrecompiler.php)). **[Inference]** A dashboard or nav in `ui`/`shared` that iterates a registry of component-name strings, filled by each module's provider, lets modules contribute widgets without the host importing their classes. Treat the component name, its public props, and its event names as the UI contract. Livewire events are browser-level, reaching only components on the same page, so durable reactions must still use Laravel events. Livewire's `->to(component: 'ns::name')` with namespaced strings is untested **[Unverified]**.

Testing works through the same resolver: `Livewire::test('billing::invoice-table')` follows the same resolution path, and Livewire's own suite tests namespaced names ([Finder/UnitTest.php](https://github.com/livewire/livewire/blob/main/src/Finder/UnitTest.php), [testing docs](https://livewire.laravel.com/docs/4.x/testing)). Colocated `.test.php` files beside SFCs need Pest pointed at the directories that hold them (the docs show `->in('Feature', '../resources/views')`) ([testing docs](https://livewire.laravel.com/docs/4.x/testing)). If the module provider is not booted in the test app, expect `ComponentNotFoundException` **[Inference]**. For the demo, keep Livewire tests under the module's `tests/` directory rather than colocating them, to avoid extra Pest glob configuration **[Inference]**.

## Recommended setup for the demo

Everything below is my recommendation **[Inference]** built on the cited findings above. Module names are illustrative; swap in the demo's real domains. Start with three feature modules plus a kernel, not one module per model.

**Tooling.** `internachi/modular` ^3.0 (3.0.2 or later), the custom namespace `Modules\` kept as is or changed through the published config, and **no** `internachi/modular-livewire` (register Livewire namespaces in each module's provider). Add `pestphp/pest ^5.3`, `larastan/larastan ^3`, `deptrac/deptrac ^4.7`, Pint, and `brianium/paratest` for parallel runs. Don't use nwidart, Cordon, or the other young packages. Revisit nwidart only if runtime module toggling becomes a requirement.

**Directory layout.**

```
resources/views/layouts/app.blade.php     # existing shell = Livewire layouts::app
app/                                       # app shell only: no domain logic
app-modules/
  shared/                                  # kernel: base types, typed IDs, event marker interfaces
    src/{Contracts,Data,Enums,Exceptions}
  ui/                                      # cross-module UI kit + widget/nav registry
    resources/views/components/            # <x-ui::...> anonymous components
    src/{Contracts,Providers}
  catalog/   orders/   billing/            # feature modules (same shape)
    composer.json                          # "require" lists only allowed module dependencies
    src/
      Contracts/  Data/  Events/  Enums/  Exceptions/  Testing/   # public
      Models/  Actions/  Listeners/  Policies/  Services/          # private
      Http/  Livewire/  Providers/                                  # private
    resources/views/{livewire,components,layouts?}
    routes/web.php
    database/{migrations,factories,seeders}
    tests/{Unit,Feature,Livewire,Contract}
tests/{Arch,Integration}
```

**Boundary rules.** (1) Public namespaces are `Contracts`, `Data`, `Events`, `Enums`, `Exceptions`, and `Testing`; every other namespace in a module is private to it. (2) A module may reference another module's public namespaces only if its own `composer.json` requires that module; an undeclared edge is a violation. (3) `Shared` depends on no feature module, and `ui` depends only on `Shared`. (4) No cross-module Eloquent relations. A module writes only its own tables, and foreign keys point only at stable upstream modules. (5) Synchronous cross-module reads go through a published contract returning DTOs. Side effects go through events (`ShouldDispatchAfterCommit`, IDs and scalar payloads, idempotent queued listeners). (6) DTOs are `final readonly` and live in the provider's `Data` namespace. (7) Module-owned Blade and Livewire names are prefixed (`billing::`, `<x-billing::>`); unprefixed components belong to Flux and `ui` only. (8) Livewire pages and widgets contribute to the app shell through the registry, and the host knows component-name strings, never classes. (9) Cross-module browser events follow a `module.entity.action` naming convention with scalar payloads. (10) The shared kernel stays tiny, with the removal test as its admission rule.

**Test layout.** Unit, feature, Livewire, and contract tests live in each module's `tests/`, run through the `modules:sync` testsuite (or per-module suites for `--testsuite=Billing`). `tests/Arch` holds the boundary suite and `tests/Integration` holds cross-module flows. The owner of each contract ships an in-memory fake under `Testing` plus an abstract contract test run against real and fake. Run the MySQL service in CI for integration tests rather than relying on SQLite `:memory:`, which hides collation, JSON, and locking differences. Use `LazilyRefreshDatabase` by default and truncation-style traits only for tests that commit.

**Enforcement.** Pest arch tests are the primary gate (the per-module deny-list above, plus layering rules). Deptrac holds the module-to-module graph and cycle check, with a baseline generated on day one. Larastan runs at a high level, and Pint covers style. CI order: Pint, PHPStan, Pest `Arch` suite, and Deptrac with no database, then module test jobs, then integration, with sharding for speed. Never run Tia in the main pipeline.

## Conclusion

The research reframes the tooling question. The package decision is small and reversible: InterNACHI and nwidart both leave boundaries unguarded, and modules that are Composer packages are cheap to leave. The decision that carries weight is the written public/private convention plus a failing test for each leak, since the one strong retrospective (Shopify's) shows enforcement tools drift from runtime reality and that public-API design is a separate job from dependency checking. A static suite will miss string-resolved coupling, raw SQL across tables, and shared cache keys, so the integration tests and the data-ownership rules do work that no analyzer does.

The Livewire 4 findings point to a lighter dependency footprint than the ecosystem suggests: Livewire's namespace API plus Laravel's Blade primitives replace the Livewire plugins, and the existing `layouts::app` shell means modules supply content, not chrome. The evidence for that is a source reading, so the first spike should confirm it. The Laravel-specific evidence base remains thin (blogs, one course, early-alpha tooling), which is another reason for the demo to keep its rules few, written down, and tested.
